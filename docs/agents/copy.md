# Product copy agent instructions

Read the accepted product value propositions and the matching package reference before writing or
reviewing public copy. This file applies to headings, introductions, examples, labels, package
READMEs, and decision documentation.

## Required outcomes

Every sentence must orient the reader, distinguish ownership, set an expectation, reduce
uncertainty, or enable action. Delete decorative text.

- Lead with the product, intended user, and concrete outcome. Explain architecture afterward and
  only when it clarifies a visible benefit or constraint.
- Preserve the distinct product lenses: Nexus defines state meaning and valid change; DashPanel
  determines where UI lives; DashList determines how Dashlets are organized and operated; Picodash
  integrates them.
- Use specific nouns and verbs: Panel, List, Dashlet, typed field, move, dock, reorder, bind,
  validate, persist, inspect.
- Explain unfamiliar terms through observable behavior when first introduced.
- Begin component and API documentation with one factual purpose sentence.
- Use realistic examples tied to concrete application needs.

Avoid generic claims such as “powerful,” “seamless,” “modern,” or “next-generation.” Do not use
metaphors or vague words such as “surface,” “journey,” “experience,” “ceremony,” or “specimen” in
place of concrete behavior.

Preserve the exact names `Picodash`, `DashPanel`, `DashList`, `Dashlet`, `Nexus`, and the
`@picodash` package scope. Picodash has a lowercase `d`.
