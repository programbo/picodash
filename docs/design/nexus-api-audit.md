# Nexus API design audit

Audit date: 2026-11-13. Baseline: [implemented behavior](../reference/nexus.md), [public exports and full declarations](../reference/api/nexus.md).
Recommendations below are **not implemented** by the documentation reset. Historical targets and completion percentages are not evidence of current behavior.

## Direction and priorities

The user's direction is that Nexus should be a generic state/data foundation usable in any application.
Consumers should define orientation, presentation and named interaction semantics. Nexus should make persisted and ephemeral state easy to expose.
The kernel already provides useful general machinery: JSON values, typed fields, atomic validation, synchronous adapters, revisions,
draft conflicts, persistence, migrations, documents, diagnostics and selectors. Its public contract also embeds substantial consumer semantics.

| Priority             | Work                                                                                      | Benefit                                                                     |
| -------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| First                | Define generic consumer-owned durable and ephemeral records, then extract product schemas | Fix the underlying boundary rather than relocating individual flags         |
| First                | Preserve exact value-gesture types and make optional capabilities discoverable            | Complete existing API families and reduce inference surprises               |
| Next                 | Standardize errors, results and review/plan/execute terminology                           | Make similar workflows coherent                                             |
| Next                 | Separate local inspection from Bridge transport                                           | Preserve public access without making development tooling a state authority |
| On demonstrated need | Add subset reset, mixed atomic operations and framework-neutral selectors                 | Fill useful gaps without creating convenience aliases indiscriminately      |

Prove a proposed extension with a non-dashboard consumer exposing one durable and one ephemeral record, then with Panel and Stack.
Exercise save/load/import, invalid-batch atomicity, independent consumer schemas, stale generation refusal and cleanup.
Consumers must not bypass kernel validation or access private runtime controllers. Authorization and disclosure remain separate from persistence policy.

## Orientation override

No orientation override is implemented in the consolidated public Nexus, Stack or facade exports.
The historical target describes useful consumer behavior: a control composition may need an orientation independent of its Panel's dock.
That interpretation is a design inference, not evidence of shipped behavior.

Stack should own an explicit orientation policy if horizontal/adaptive composition is supported.
Picodash can derive a suggestion from Panel placement and pass it through a public Stack API.
A standalone Stack must accept the same policy without requiring a Panel. An application may persist an override through generic Nexus data,
but Nexus should not interpret orientation. Moving this field into the kernel would deepen the boundary problem.

## APIs that overlap in appearance

| APIs                                                 | Actual distinction                                                                   | Assessment                                                                                                                           |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| `setValue(handle, value)` / `setValues(record)`      | Root-owned typed handle versus atomic keyed batch                                    | Useful alternatives; document handle ownership and unknown-key behavior.                                                             |
| `setInput(binding, input)` / canonical setters       | Draft, parse and conflict handling versus direct canonical writes                    | Different semantics. Canonical setters must not be presented as a substitute for editor input.                                       |
| Value and numeric gestures; field and input gestures | General versus number-specific typing; direct field versus bound editor              | One shared controller is sensible. Keep convenience only for stronger contracts and preserve precise field value inference.          |
| Root / scoped commands                               | Explicit scope ID versus addressed receiver                                          | Useful ergonomics; keep one underlying command definition to prevent drift. Scoped values are still shared globally.                 |
| Result methods / `OrThrow`                           | Rejected data returned versus exception flow                                         | Intentional choice. A typed result-unwrapping helper may scale better than adding dozens of exception variants.                      |
| Pure document utilities / `documents` namespace      | Data transformation versus identity/policy/freshness-checked operations              | Different authority. Decoding a document does not authorize an import. Consider a dedicated document entrypoint for discoverability. |
| Snapshots / diagnostics / events / Bridge inspect    | Current state / current health / temporal observations / disclosed remote projection | Complementary channels. Bridge must not replace ordinary local observation.                                                          |
| External value adapter / Bridge named observations   | Writable canonical owner versus read-only application results                        | Different authority. Progress and computed results need not become writable Nexus fields.                                            |
| Persistence envelope / portable document             | Storage identity, revisions and conflicts versus policy-controlled import/export     | Keep their distinct purposes; share implementation only where contracts agree.                                                       |
| Facade reexports / foundation exports                | Integrated convenience versus standalone products                                    | Useful composition, provided explicit exports and behavior references do not drift.                                                  |

## Generic runtime inspection and Bridge ownership

The current public Nexus entrypoints expose snapshots, subscriptions, diagnostics, leases and events.
They do not expose `inspectRuntime` or arbitrary application-object reflection. Private runtime-controller helpers remain implementation details.

Local inspection makes sense for Nexus-owned facts any application needs: declared fields, capabilities, exposed durable/ephemeral records,
resource identity and current health. Bridge owns discovery, authentication, disclosure, allowlisted writes, remote waits, generation fencing,
transport limits and bounded event cursors. This is a layered relationship rather than competing stores.

The implemented `PicodashDevBridgeObservationSource` already provides generic read-only application observations through `getSnapshot`/`subscribe`
and an `observationNames` allowlist. It is suitable for progress, jobs or computed results. It is not a replacement canonical state authority.
If multiple local consumers need the same observation abstraction, a small consumer-neutral contract may be useful.
Do not put it into Nexus solely because Bridge consumes Nexus; demonstrate the local state-management benefit first.

## Completion criteria for the next design round

Agree the smallest generic durable/ephemeral record contract and its owners. Prove a non-dashboard consumer and existing consumers together.
Preserve strict JSON, atomic validation, adapter ownership, revision/freshness fencing, deterministic recovery and teardown.
Then remove specialized schemas across setters, serialization, documents, migrations, recovery, leases and exports.
Regenerate the API inventory and record measured consumer results instead of milestone percentages.
